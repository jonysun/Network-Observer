# 数据采集、聚合、传输与丢弃架构

[返回中文首页](../README.zh-CN.md) · [安装与运维指南](installation.zh-CN.md)

本文说明 Network Observer 如何在不降低采集频率、字段颗粒度和计数精度的前提下，解决每秒每个连接都写入 WAL、重复发送累计行造成的数据量暴涨问题。

## 目标和边界

Agent 仍然按照配置周期完整读取可用的 socket、Socket Diag、conntrack、eBPF 字节计数、进程/cgroup、Docker、DNS 和邻居数据。默认端点采集周期约为 1 秒；具体值由配置决定。优化只改变“同一份数据怎样在本地合并、怎样在线发送和怎样持久化”，不删除以下字段：连接、flow_id、IPv4/IPv6、源/目的端口、网卡、网络命名空间、进程、容器、NAT 元组、方向字节、包数、采样率、观测来源、时间覆盖区间、归属和降级原因。

Agent 的实时页面和历史分析是两条用途不同的路径：实时页面需要当前活动流的最新状态，历史分析需要每分钟的流量和 presence 汇总。不能把历史累计行当成当前 socket，也不能用降低采集频率来解决存储压力。

## 1. 本地完整采集

每一个采集周期执行以下步骤：

1. 读取所有可用观测源，生成当前周期的完整观察集合。
2. 给每条观察保留稳定的 `flow_id`、设备、观测点、接口、网络命名空间、元组、进程/容器归属和方向计数。
3. 对字节和包计数使用本周期增量；总计数和速率字段保留最近一次采样值。
4. 对本周期不存在的活动流生成关闭状态，使实时端能够准确移除已经结束的连接。
5. 如果采集源失败，不把失败当成“没有连接”，而是记录 `data_gap` 或能力降级状态。

当内核、权限、流量卸载或网关采样无法提供某个字段时，字段保留未知并上报能力状态；这和本地聚合无关，也不会把未知字段伪装成已知。

## 2. 本地实时状态

Agent 在内存中保存每个活动流的完整最新状态：

- `realtimeLatest` 保存当前所有活动流的最新快照。
- `realtimePending` 以“观测点 + flow_id”为键，只保留每个流尚未发送的最新变化。
- 一个连接在 1 秒内发生多次变化时，线上只发送最后一个变化；最后状态已经包含最新字节增量、速率、状态和归属字段。
- 采集仍然每秒执行，只有相同状态的重复在线快照不再反复发送。
- Agent 断线重连后先发送完整活动快照，再发送后续变化。
- 活动流从下一次完整采集集合中消失时，Agent 发送关闭事件；没有显式关闭事件的采集器也能通过集合差异生成关闭事件。

因此，Center 看到的实时连接仍然包含连接、IP、端口、网卡、进程和容器颗粒度，只是对稳定不变的连接避免重复传输。

## 3. 本地历史聚合

历史数据按 `flow_id + 分钟 + 连续观测 segment` 聚合：

- 当前分钟的记录只在内存累计，不在每个采集周期重复写 WAL。
- 字节和包字段按每次采集的增量精确相加，不用最后一次累计值覆盖前面的增量。
- `first_seen`、`last_seen`、活动秒数、上下行流量和包数都由原始观察计算。
- 连接跨分钟时生成下一分钟记录；采集间断超过允许窗口时生成新的 segment，避免把没有观测到的时间误算为在线。
- 分钟结束后写入一条带稳定 `history-*` ID 的累计行。若 WAL 或网络暂时不可用，该聚合保持 dirty 并重试。
- Agent 正常退出时会强制刷出当前分钟；非正常断电时由 WAL 和明确的数据缺口标记表达可能缺失的区间。

这使 1,000 条活动连接每秒约 1,000 次完整采集仍然成立，但历史 WAL 从“每秒重复累计连接行”变为“每条流每分钟一条累计记录”。原始采集精度保持在 Agent 内部，历史落盘粒度保持为分钟汇总。

## 4. WAL 和确认

WAL 只承载需要可靠补传的数据：

- 已完成或被强制刷出的分钟历史聚合。
- DNS 元数据观察。
- 显式的数据缺口记录和顺序信息。

每条 WAL 记录有单调序列号。Center 按批处理接收并返回确认序列号；Agent 只有收到完整确认后才回收对应 WAL 空间。重连时从最后确认序列号继续补传，重复批次由 Center 的序列检查和 ClickHouse 的稳定 event key/版本处理。

正常 WAL 容量内不主动丢数据。如果 WAL 达到容量或记录超过保留时间，Agent 不静默丢弃，而是报告 `data_gap`、保留可用的最新状态，并在能力页显示缺口原因。容量耗尽属于明确降级状态，不是正常采集策略。

Agent 对尚未进入 WAL 的内存队列设置独立上限：历史聚合最多保留 100,000 条或约 64 MiB，DNS 元数据最多保留 50,000 条或约 16 MiB。只有 WAL 已满、ACK 长时间无法推进并且这些内存上限也耗尽时，才丢弃最旧的未持久化聚合或 DNS 记录，并持久记录 data_gap 计数和原因。丢弃历史聚合会清除该流的连续性游标，下一次观察从新的 segment 开始，避免把未观测区间错误算成持续在线。这个边界保护 Agent 内存，不改变采集周期或观测字段。正常 WAL 可写时不会调用淘汰逻辑；只有 WAL 返回容量或保留期压力后，内存边界才会生效。历史行确认使用稳定 ID 索引，确认成本与本批记录数线性相关，不会随着全部聚合记录做全表扫描。

## 5. Center 接收和查询

Center 对持久观察执行以下顺序：

1. 校验设备凭证、顺序和观测字段。
2. 应用归属规则、DNS 关系和 ASN/GeoIP 丰富化。
3. 将历史行写入 ClickHouse 的分钟流量和 presence 表。
4. 只有新鲜的非 `history-*` 观察才进入短期实时缓存。
5. WebSocket 只广播实时变化；历史 WAL 补传不会把旧分钟行广播成当前连接。

实时查询会合并短期实时缓存和仍在 TTL 窗口内的活动表，并按 `device_id + flow_id` 去重，实时缓存优先。Agent 重连认证成功时先清理该设备的旧实时缓存，再接收新的完整快照，防止上一次连接残留的流继续显示。

历史查询直接使用 ClickHouse 的分钟汇总，保留设备、网卡、协议、IP、端口、进程、容器、域名、ASN、国家/地区/城市和可信标记等分析维度。历史记录不会因为实时增量合并而改变原始时间覆盖和字节总量。

## 6. ClickHouse 表和重复计数保护

`connection_presence_minute` 使用 `ReplacingMergeTree(version)`。历史聚合的 `event_key` 由稳定的 `history-*` ID、分钟和维度构成，重试时替换同一逻辑行，而不是把同一累计分钟再次相加。旧版 `MergeTree` 表升级时会复制到显式 schema 的 ReplacingMergeTree 临时表，再重命名正式表，并保留带时间戳的旧表备份。

历史聚合行不会写入 `live_connections`，避免一分钟历史行在实时活动查询中被误判为当前 socket。实时路径和历史路径在查询层保持分离。

## 7. 统计口径

- 实时连接数：当前短期缓存和活动表合并后的不同 `device_id + flow_id`。
- 历史连接数：时间窗口内不同 `flow_id` 的 presence 记录，属于观测到的流数量，不是逐连接回放。
- 流量：按 Agent 能提供的方向增量累加；网关采样流量保留 `estimated` 标记。
- 本机主动发起、外部主动访问和未知：只有 eBPF `connect/accept` 或 conntrack 原始方向证据明确时才分类，其余保留未知。
- 重复的 Agent/网关观测：通过观测点、NAT 元组、时间窗口和关联键做去重或视角关联，不能在证据不足时假设两条记录等价。

## 8. 这次优化带来的实际变化

优化前，同一条稳定连接会把累计状态反复写入 WAL，导致待确认记录数量接近“连接数 × 采集周期”。优化后：

- 采集次数不变。
- 实时仍保留每个活动连接的最新状态。
- 网络发送只保留每个流最新变化，并在重连时补完整快照。
- 历史 WAL 以分钟累计行承载，不再按秒重复写累计行。
- 字节、包数、分钟 presence 和连接字段不会因为压缩传输而降低精度。
- 只有 WAL 超限、采集源失败或能力不可用时才产生明确的数据缺口或未知字段。

部署升级后，旧版已经写入的重复历史行不会被静默删除；迁移会保留旧表备份。新版本从升级时刻开始使用稳定 event key 和分钟聚合，旧 WAL 会按照原顺序补传并在 Center 端按新旧协议分别处理。
