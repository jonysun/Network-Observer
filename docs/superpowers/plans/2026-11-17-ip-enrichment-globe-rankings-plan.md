# 远端 IP 归属、连接发起方、实时地球与排名实施计划

本计划依据已确认的设计规格 `docs/superpowers/specs/2026-11-17-ip-enrichment-globe-rankings-design.md`。首期继续使用现有 Center、PostgreSQL、ClickHouse、Agent、REST、WebSocket 和 Vue，不新增服务。

## 阶段 1：数据库契约与 IP 手工元数据

1. 在 PostgreSQL 增加按规范化 IPv4/IPv6 地址唯一的 IP 手工覆盖表，支持域名、ASN、组织、国家/地区/城市、坐标和可信标记的字段级空值覆盖；记录操作者和更新时间。
2. 为 PTR 缓存建立持久状态，覆盖成功、无记录、临时错误、过期时间和最近查询时间；查询任务异步执行，增加并发与每 IP 限速，私网及保留 IP 不入队。
3. 在设备档案表增加可空纬度/经度，验证取值范围；扩展已有设备档案更新与查询方法，不改变现有命名、类别和在线状态语义。
4. 增加 IPv4/IPv6 规范化、手工字段保存/清除、可信标记、坐标校验、PTR 缓存过期/失败重试和审计测试。

阶段退出条件：同一规范 IP 的手工值跨 Agent 一致；逐字段清除后恢复自动值；无效 IP/坐标被拒绝；PTR 不阻塞流量写入且不会查询非公网地址。

## 阶段 2：Agent 连接发起方证据

1. 扩展 `proto/networkobserver/v1/agent.proto` 和 `internal/domain`，定义独立于 `local_is_source` 与字节方向的连接发起方、首次观察方向、证据来源和未知状态；按仓库现有流程重新生成 Go 绑定。
2. 为 Linux Endpoint Agent 增加 connect/accept 生命周期观测，并把生命周期事件关联到 socket inode/tuple。不得采集应用载荷；事件丢失、权限不足、内核不支持、Agent 启动前已存在的连接均保持未知。
3. 为 Endpoint 能力状态单独报告发起方采集能力。该能力不可用时，其余 Socket Diag、procfs、eBPF 字节计数和进程归属采集继续运行。
4. 为 Gateway Agent 保留 conntrack original tuple 的起始方向；只在本地接口/已知 LAN 前缀能够唯一判定 LAN 与外部侧时映射到本地/远端发起，否则报告未知。UDP 首次方向使用独立枚举，不标成 TCP 发起方。
5. 覆盖主动 connect、被动 accept、已有连接、重连、NAT、事件丢失、无 BTF/权限、网段不明、UDP 首包和方向不确定等测试。

阶段退出条件：发起方绝不由上传/下载方向或端口号推断；不确定值均为未知且有原因；关闭新生命周期采集不影响已有采集功能。

## 阶段 3：兼容的 ClickHouse 历史结构

1. 为 `live_connections` 增加连接发起方及证据字段；确认现有 WebSocket/REST 读取和 ReplacingMergeTree 兼容。
2. 为 `traffic_minute` 新写入增加规范化远端 IP 和连接发起方快照；保留现有 event key、上传/下载定义、估算标记、TTL 和数据缺口字段。
3. 为 `connection_presence_minute` 增加排名与发起方分析需要的远端 IP、接口、本地端口、进程/容器及发起方/证据字段；保证一条 flow 的重复观测不会重复计数。
4. 迁移仅使用可重复执行的 `ADD COLUMN IF NOT EXISTS` 等兼容语句；旧数据不回填猜测值，以 unknown/字段不可用标识。
5. 增加迁移、旧行读取、TTL、方向归一化、IPv6 远端地址、进程/端口聚合和跨 Agent 重复观测测试。

阶段退出条件：现有卷升级后表结构迁移可重复执行；既有记录和 TTL 不丢失；新观测能查询到正确的本地/远端角色和起始证据。

## 阶段 4：Center 归属、审计与查询 API

1. 扩展 `Store` 的 IP enrichment：自动结果来自本地 MMDB，最终字段按“手工覆盖 > 有效 DNS 关系 > PTR”或适用字段优先级组合；响应同时保留自动值、手工值、来源、更新时间、GeoLite 版本、可信标记和未知原因。
2. 增加 `PATCH /api/v1/ip-metadata`，要求现有管理员认证；明确 JSON 字段省略表示不更新、显式 null 表示清除手工覆盖。写操作进入现有审计日志。
3. 扩展 `GET /api/v1/enrichment`，保持现有 `items` 响应兼容；支持批量上限和 IPv4/IPv6 输入。
4. 将连接发起方、证据来源和状态写入实时 REST/WebSocket 负载；为实时连接查询增加白名单发起方筛选，不改变上传/下载筛选。
5. 增加 `GET /api/v1/overview/rankings`：固定默认 24 小时，维度白名单、最大 Top N、请求超时和并发上限；按“榜单维度 + device + remote_ip”分别算字节和 distinct `(device_id, flow_id)`，再由 Center 应用当前手工覆盖/可信状态并聚合显示桶。
6. 四组默认结果为 Agent、远端域名、Agent+本地端口、Agent+进程；支持远端 IP、网卡、ASN、国家/地区/城市、容器和连接发起方筛选/分组。域名歧义/未知不重复累计字节。
7. 查询必须返回历史维度可用性、估算、数据缺口和部分结果状态；超过中间聚合上限时明确降级，禁止静默返回看似完整的错误总数。
8. 测试权限、请求验证、字段级清除、审计、DNS TTL/PTR 优先级、可信过滤、所有维度计数、时间边界、未知字段、查询上限和跨数据库聚合。

阶段退出条件：API 可通过 PostgreSQL 手工元数据展示当前覆盖而不改写 ClickHouse；字节和连接数不双计；旧历史明确显示缺失；非管理员不能读写受保护端点。

## 阶段 5：Vue 元数据编辑与连接角色

1. 扩展类型安全的 API client、请求状态与错误处理；在实时连接表中独立显示 TCP 发起方或 UDP 首次观察方向、证据来源和未知原因，并提供筛选。
2. 从连接、排名和可定位的地球路线打开统一 IP 详情面板；分开呈现自动识别、手工覆盖、来源、可信、更新时间和审计变化；支持逐字段清除与保存。
3. 在设备档案编辑中加入可选经纬度输入、边界校验和清除；设备列表展示坐标是否已配置。
4. 为请求失败、空结果、PTR 等待、无 MMDB 匹配和无可信来源设计明确状态；不因详情面板或 API 错误导致整页空白。

阶段退出条件：手工值优先级肉眼可辨；清除恢复自动值；上传/下载列不被发起方标签覆盖；键盘可访问详情面板和筛选控件。

## 阶段 6：Three.js 实时地球

1. **开始 Web 代码前**先运行 `modern-web-guidance` 要求的检索，核对 Three.js、WebGL 资源释放、可访问交互、尊重 `prefers-reduced-motion` 和移动性能指南；按检索结果确定依赖版本及具体场景实现。
2. 选择可随构建打包、许可明确的低分辨率陆地几何数据，生成青绿色点阵球体、经纬网和地球曲面路线；不调用第三方地图服务。
3. 从已有连接 WebSocket 聚合 Agent+远端 IP 活动连接，按双向速率排序，最多绘制 100 条路线。用稳定对象更新 buffer/geometry，避免每条消息重建场景。
4. Agent 坐标使用设备档案人工位置；终点用 IP 手工坐标或 MMDB 坐标。无任一端坐标时不画线并计入未定位数量。
5. 增加 Agent/可信筛选、暂停/恢复、旋转/缩放、恢复视角、路线悬浮与键盘聚焦详情；WebGL 错误或不支持时降级展示状态及现有连接列表。
6. 释放 renderer、几何体、材质、事件和动画帧；在系统减少动态效果时停用自动旋转。

阶段退出条件：桌面和窄屏画面稳定、地球非空、路线坐标正确、交互可用；组件卸载后无重复渲染和资源累积；WebGL 不可用不会破坏其它总览信息。

## 阶段 7：24 小时多维总览

1. 在总览加入四组默认榜单，统一 24 小时窗与可信筛选；每行展示总流量、上传、下载、distinct flow 数、估算和数据缺口。
2. 每组默认显示 Top 10，允许展开最多 50 项；增加维度切换并与 IP 详情、实时连接筛选联动。
3. 展示历史数据能力提示：流量已有但新增的本地端口/进程/发起方 Presence 尚未覆盖的时间段明确标为不可用，不补造旧数据。
4. 做空、加载、错误、查询降级、未知域名、歧义域名、可信筛选和响应式状态。

阶段退出条件：四组默认榜单和所有规格维度能相互筛选联动；切换过滤条件不产生旧响应覆盖新状态的竞态。

## 阶段 8：端到端验证、文档与发布

1. 运行 `go test ./...`、`go vet ./...`、Web `npm run build`、ClickHouse/PostgreSQL 迁移测试、Compose 配置校验和 Center/Agent 镜像构建。
2. 用浏览器验证桌面与移动视口，保存 Playwright 截图；检查 WebGL canvas 非空像素、旋转、筛选、连接更新和坐标缺失降级。
3. 构造 IPv4/IPv6 TCP/UDP、出站/入站、NAT、未知发起方、私网和公网 ASN/GeoIP、DNS/PTR、手工覆盖、可信筛选、连接关闭及历史窗口边界场景。
4. 执行 10 个端点、1 个网关、10,000 条活动连接压力验收，确认总览查询不会阻塞采集，排名/实时路线资源有上限，Prometheus 标签保持低基数。
5. 更新中文 README 和安装文档：字段来源和可信度、PTR 缓存/限速、发起方未知条件、UDP 语义、GeoIP 近似性、Agent 手工坐标、历史迁移限制及 Lucky API 暂未接入。
6. 以固定版本构建并发布多架构 Center 镜像与 Agent 二进制；验证已有 Compose 和原生 systemd Agent 升级路径。Lucky API 接入不在本轮发布内容中。

阶段退出条件：自动化检查通过，端到端验收记录清楚；旧 Agent/旧数据库升级时仍能运行，旧数据不丢失，新 Agent 能逐项报告能力和降级原因。

## 依赖与执行顺序

按阶段 1 → 2 → 3 → 4 → 5 → 6/7 → 8 推进。阶段 6 和阶段 7 可在 API 契约稳定后并行开发，但必须共用已确认的远端 IP 元数据与连接发起方模型。发布前完成阶段 8 的全部检查。

## 回滚策略

- Agent 可关闭新连接生命周期采集能力；关闭后仅发起方字段变为未知，其余连接与字节采集保持运行。
- ClickHouse 使用可重复的增量迁移，不要求立即删除新列/表；旧 Center 版本忽略新增列。
- Web 可回退到旧镜像，数据库中的审计、手工元数据和新增历史数据保留。
- PTR worker 可通过 Center 配置关闭；禁用只使 PTR 来源未知，不影响 DNS、MMDB 和观测接收。

## 本轮明确不做

- 逐连接历史归档或历史地球路线回放。
- 从任意 HTTP 请求头读取 X-Forwarded-For、通用访问日志采集，或本轮接入 Lucky API。
- 根据端口经验、字节方向或单纯公网/私网猜测 TCP 发起方。
- 因新功能改变路由、防火墙、Docker 网络、conntrack 内核参数或采集普通应用载荷。
